Background

말투는 바꾸되,
하려던 말은 바뀌면 안 됩니다

상사에게 보내는 말과 친구에게 보내는 말은 다릅니다. 그래서 "고쳐 쓰되 사실과 의도는 건드리지 않는다"를 가장 먼저 정했습니다.

팀원 셋이 비전공자라 개발은 제가 전부 맡았고, 팀원들은 평가 사례와 루브릭을 CSV로 만들어 PR로 올렸습니다.

SOLUTION · 검증을 통과해야 나가는 구조
메시지 + 받는 사람상사 · 친구 · 고객 … ↓ 첨삭 생성LangGraph · Claude ↓
규칙 검증사실 · 의도 · 말투 →통과→ 결과 표시
↓ 실패
1회 재생성 후 재검증 →또 실패→ 원문 반환

Background

하나만 잘못 올려도
바로 손해가 납니다

마진 계산을 틀리거나 통관이 안 되는 상품, KC 인증 대상 상품을 놓치면 돈이나 법 문제로 이어집니다. 그래서 이런 판단은 LLM에 맡기지 않기로 했습니다.

상품 출처, 판매 채널, 저장소는 인터페이스로 분리해 채널을 추가하거나 DB를 바꿔도 나머지 코드는 그대로입니다.

SOLUTION · 코드가 정하고, LLM은 세 곳에만
소싱→ 통관·인증
필터→ 마진 계산→ 적자 주문?사람 승인→ 등록 · 발주
코드 · 같은 입력이면 같은 결과 → 테스트 가능
상품성 평가Gemini 상세페이지 작성DeepL 번역 후 다듬기 고객 문의 응대민감 문의는 사람에게
LLM · 사람이 판단하던 부분만

배운 점LLM을 어디에 쓸지보다 어디에 쓰지 않을지를 먼저 정하니, 무엇을 테스트해야 하는지가 분명해졌습니다.

Background · SolutionCodeSage

Background

LLM은 Webhook이
기다려 주는 시간보다 느립니다

GitHub Webhook은 응답이 늦으면 실패로 처리하는데, PR이 조금만 커도 LLM 호출이 그 시간을 넘깁니다. 그래서 Webhook은 서명만 확인하고 바로 응답하고, 실제 리뷰는 Redis 큐 뒤의 Worker가 따로 처리하도록 나눴습니다.

SOLUTION · 응답과 리뷰를 분리
GitHubPR 이벤트→ APIHMAC 검증 · 즉시 응답→ Redis 큐→ Worker바뀐 diff만 리뷰→ PR 코멘트
설치 토큰JWT로 발급 · 캐싱 프롬프트 방어PR 본문 속 숨은 지시문 차단 Docker Composeapi · worker · redis · postgres
보안 · 운영

Result · Lesson LearnedCodeSage

Result

4개컨테이너를 한 번에 실행
바뀐 부분만 다시 리뷰새 커밋이 올라와도 같은 지적이 반복되지 않고, 토큰도 덜 씁니다.

Lesson Learned

결정Webhook 요청 안에서 바로 리뷰하는 대신 Redis 큐와 Worker로 나눴습니다. GitHub이 정한 응답 시간과 LLM이 걸리는 시간을 서로 묶지 않기 위해서입니다.

배운 점외부 서비스와 연동할 때는 기능보다 그쪽의 시간 제한과 재시도 방식을 먼저 확인해야 합니다.
